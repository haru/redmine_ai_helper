# ADR-005: Write-tool classification via a `define_function` DSL attribute for read-only mode

**Date**: 2026-07-18
**Status**: Proposed

## Context

GitHub issue #344 asked for a global "read-only mode" that guarantees the AI Helper chat cannot modify Redmine data (create/update issues, create/update/delete wiki pages), regardless of what the user asks for or how the LLM is prompted. The plugin exposes write operations as five `BaseTools`-generated functions: `IssueUpdateTools#create_new_issue`, `IssueUpdateTools#update_issue`, and `WikiWriteTools#wiki_add_page` / `#wiki_update_page` / `#wiki_delete_page`. These tools are consumed from three independent surfaces: (1) `BaseAgent#available_tool_classes`, which feeds every agent's `RubyLLM::Chat#with_tools`, (2) `McpServerLoader`-generated `SubMcpAgent` classes representing external MCP servers, and (3) `RedmineAiHelper::Mcp::Server`, which publishes a `tools/list` to external MCP clients and validates `tools/call` requests.

A prompt-instruction approach ("do not write data when read-only mode is on") was rejected up front per the project's security-first principle: prompts are not a reliable enforcement boundary, and the guarantee must hold even against an adversarial or confused model.

## Decision

1. **Tag write intent at the DSL level.** `BaseTools.define_function` gains a `write:` keyword (default `false`). Each generated `RubyLLM::Tool` subclass gets a `write_tool?` singleton method returning that value. The five write functions above are the only call sites passing `write: true`.
2. **Enforce by omission, not refusal.** `BaseAgent#available_tool_classes` filters out `write_tool?` tool classes when `AiHelperSetting.read_only_mode?` is true, before the tool list ever reaches `RubyLLM::Chat#with_tools`. The LLM is simply never given the capability to call these functions — there is no code path where a write tool is provided and then a runtime check rejects the call.
3. **Disable, don't filter, for external MCP agents.** `SubMcpAgent#enabled?` (generated by `McpServerLoader`) returns `!AiHelperSetting.read_only_mode?`. External MCP servers are opaque (their tool set isn't known to have `write_tool?` classification), so the whole agent is excluded from `AgentList#list_agents` rather than attempting per-tool filtering.
4. **Mirror the exclusion on the outbound MCP server.** `RedmineAiHelper::Mcp::Server.collect_tools` excludes `write_tool?` tools from the published `tools/list`, and `Server.tool_call_permitted?` additionally rejects `tools/call` for any write tool name as defense in depth, independent of whether the client saw it in the list.
5. **One boolean setting, no scope.** `AiHelperSetting#read_only_mode` (default `false`) is a single global flag, consistent with `mcp_server_enabled` and `send_user_id_enabled`. No per-project or per-role variant is introduced (YAGNI); it can be layered on later if a real need arises.

## Consequences

**Positive**:
- The guarantee is structural: an agent whose tool list has no write tools cannot cause a write, independent of prompt wording or model behavior.
- Adding a new write tool anywhere in the codebase requires exactly one line (`write: true` on its `define_function`) to be covered by all three enforcement surfaces simultaneously, since all three consume the same `write_tool?` metadata.
- Existing `define_function` call sites are unaffected: the keyword defaults to `false`, so `write_tool?` is `false` and behavior is unchanged when read-only mode is off.

**Negative**:
- Classification is manual and per-function; a new write-capable tool that omits `write: true` would silently leak through. This risk is mitigated by tests asserting `write_tool?` on every known write tool, but there is no static enforcement that *all* mutating tools are tagged.
- External MCP servers are excluded entirely rather than filtered per-tool, so read-only external MCP tools also become unavailable while read-only mode is on. This trades completeness for safety, since the plugin cannot introspect whether an external server's tools are safe.

## Alternatives Considered

- **Prompt-only enforcement**: rejected outright — does not meet the security-first requirement; a model can be coerced into calling a tool it was told not to use.
- **Runtime guard inside each write tool method** (raise if read-only): rejected because it still hands the LLM the tool definition (name, description, schema), inviting failed/retried calls and wasted tokens, and because it duplicates the same conditional five times instead of once in `available_tool_classes`.
- **Naming convention instead of a DSL attribute** (e.g. tool name prefix): rejected as fragile and undiscoverable — `write_tool?` is explicit, greppable, and enforced at the point of definition.
- **Per-tool filtering for external MCP agents**: rejected for this iteration because external MCP tool schemas carry no write/read classification the plugin can trust; disabling the whole agent is the conservative, correct default (User Story 2, P2).
