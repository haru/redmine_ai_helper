# Agent Write-Capability Routing

Bug: `LeaderAgent` picked the agent for a step from backstory wording alone,
so "create an issue" requests were assigned to `issue_agent` (which holds no
write tools). The step silently never ran, yet the final answer still
reported the issue as created (S016).

## Decision

- **`BaseAgent#can_write?`** = `available_tool_classes.any?(&:write_tool?)` —
  reuses the existing `write_tool?` metadata from the
  [Tool System](./tool-system.md) DSL rather than adding a new declaration
  mechanism (S016).
- **Never exposed to the router**: `AgentList#list_agents` still returns only
  `agent_name`/`backstory`. Dual-role agents such as `wiki_agent` (holds both
  `WikiTools` and `WikiWriteTools`) would otherwise read as "write
  specialists" and get excluded from read-only assignments. Correct routing
  instead comes from rewording the `issue_agent` / `issue_update_agent`
  backstories so a create request can no longer be misread as something
  `issue_agent` handles (S016).
- **Runtime guard, not pre-validation**: `generate_steps`'s structured output
  gains a required `requires_write` boolean per step (one extra field, same
  LLM call). Immediately before dispatch, `LeaderAgent#execute_chat_room_steps`
  checks `step["requires_write"] && !agent.can_write?`; a match skips the LLM
  call and records the step as a structured failure in
  `ChatRoom#step_results`. No automatic re-routing — that would hide the
  routing failure and risks silently picking a different write agent (S016).
  This same path also covers read-only mode, since `can_write?` becomes
  `false` for every tool-classified agent once read-only mode filters out
  `write: true` tools.
- **Skipped steps stay visible to later steps**: `record_skipped_step` also
  appends a notice to the shared `ChatRoom` message history, not just
  `step_results` — otherwise an agent handling a later step (e.g. "add a
  comment to the issue created above") would act on results that never
  existed (S016).
- **Final answer is grounded in execution results, not just presumed
  success**: `LeaderAgent` passes the accumulated `{agent, step, status,
  error}` results into `generate_final_response` (all 8 locales), replacing
  wording that presupposed every step completed. The instruction
  deliberately separates two things a naive "use only these results as
  facts" phrasing would conflate: execution results decide *which steps
  succeeded*; the answer's *content* (issue IDs, retrieved data) still comes
  from agent replies in the conversation history, since the results array
  never carries it (S016).
- **Unclassifiable tools default to write-capable, not read-only**: MCP
  agents generated by `McpServerLoader` override `available_tool_classes`
  with `RubyLLM::MCP::Tool` instances that don't respond to `write_tool?` at
  all. `can_write?` is overridden to `true` there instead of guarded with
  `respond_to?` — silently resolving "can't classify" to "can't write" would
  make legitimate MCP write steps fail with no diagnosable cause. Read-only
  mode still fully disables these agents via the pre-existing `enabled?`
  override, so this path is unreachable in that mode. See
  [MCP Integration](./mcp-integration.md) (S016).

## Rejected alternatives

- Adding `can_write` to `list_agents` and a routing rule to the planning
  prompt: rejected — it would label dual-role agents as write-only and block
  read-only steps from ever reaching them (S016).
- A dedicated plan-validation phase before execution: rejected — it
  duplicates the per-step guard and still needs its own read-only-mode
  handling (S016).
- Guarding `can_write?` with `respond_to?(:write_tool?)`: rejected as the
  same class of silent-failure fallback this decision exists to remove
  (S016).
- Automatically re-routing a misassigned step to a capable agent: rejected —
  hides the routing failure from the user (S016).
