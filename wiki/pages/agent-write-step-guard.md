# Write-Capable Step Guard

Split from [Agent Write-Capability Routing](./agent-write-capability-routing.md)
when that page passed the 600-word limit. That page decides *how an agent's
write capability is defined and kept out of routing*; this one covers what
happens at dispatch when the step and the agent disagree, and how the answer
reports it.

## A runtime guard, not pre-validation

`generate_steps`'s structured output gains one required `requires_write` boolean
per step — one extra field, the same LLM call. Immediately before dispatch,
`LeaderAgent#execute_chat_room_steps` checks
`step["requires_write"] && !agent.can_write?`; a match skips the LLM call and
records the step as a structured failure in `ChatRoom#step_results`. There is
**no automatic re-routing**: it would hide the routing failure and risks
silently picking a different write agent (S016).

The same path also covers read-only mode, because `can_write?` becomes `false`
for every tool-classified agent once read-only mode filters out `write: true`
tools — no second mechanism is needed (S016).

## Skipped steps stay visible to later steps

`record_skipped_step` appends a notice to the shared `ChatRoom` message history,
not only to `step_results`. Otherwise an agent handling a later step — "add a
comment to the issue created above" — would build on results that never existed
(S016).

## The final answer is grounded in what ran

`LeaderAgent` passes the accumulated `{agent, step, status, error}` results into
`generate_final_response` (all 8 locales), replacing wording that presupposed
every step completed. The instruction deliberately separates two things a naive
"use only these results as facts" phrasing would conflate: execution results
decide *which steps succeeded*, while the answer's *content* — issue IDs,
retrieved data — still comes from agent replies in the conversation history,
which the results array never carries (S016).

## Unclassifiable tools default to write-capable

MCP agents generated by `McpServerLoader` override `available_tool_classes` with
`RubyLLM::MCP::Tool` instances that do not respond to `write_tool?` at all.
`can_write?` is overridden to `true` there rather than guarded with
`respond_to?`: silently resolving "cannot classify" to "cannot write" would make
legitimate MCP write steps fail with no diagnosable cause. Read-only mode still
disables these agents entirely through the pre-existing `enabled?` override, so
the permissive default is unreachable in that mode (S016). See
[MCP Integration](./mcp-integration.md).

## Rejected alternatives

- A dedicated plan-validation phase before execution: rejected — it duplicates
  the per-step guard and still needs its own read-only-mode handling (S016).
- Guarding `can_write?` with `respond_to?(:write_tool?)`: rejected as the same
  class of silent-failure fallback this decision exists to remove (S016).
- Automatically re-routing a misassigned step to a capable agent: rejected — it
  hides the routing failure from the user (S016).
